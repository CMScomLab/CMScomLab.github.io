# CMScomLabブログの作成・更新

## 必ず行うこと

1. `git status --short --branch` で作業状態を確認し、既存の変更を保護する。新規作業では、指定がなければ `codex/` 接頭辞の作業ブランチを作る。
2. 記事を書き始める前に、依頼された主題、技術名、プロジェクト名、主要なキーワードを `docs/blog/posts/` と `docs/projects/` から検索する。関連エントリーと直近のエントリーを読み、語調、見出し、用語、リンク方法を合わせる。
3. 既存記事と主題や結論が重なる場合は、原稿を作る前にユーザーへ次の点を確認する。
   - 今回新しく追加された事実、成果、実験結果は何か
   - 前回の記事から変わった判断、実装、規模、公開範囲は何か
   - 新規記事として分けるのか、既存記事を更新するのか
   回答を受けたら、新しい報告が冒頭で分かる構成にし、既存記事へリンクする。
4. 新規記事を `docs/blog/posts/YYYY-MM-DD-<slug>.md` に置き、次のフロントマターを設定する。
   - `date`
   - `authors`（通常は `terapyon`）
   - `categories`
   - `tags`
   - `slug`
   - `title`
5. フロントマターの `title` と本文のH1を一致させ、導入部の後に `<!-- more -->` を入れる。
6. サイト内の記事には、投稿ファイルからの相対リンクを使う。外部リンクには原則としてHTTPSの正規URLを使う。
7. 研究、特許、顧客、未公開技術に関する記述は、ユーザーが明示した公開範囲を越えて具体化しない。断定の強さも提供された事実に合わせる。
8. 初稿と改稿の提出前に、下記「タイトル・大見出しの検査」を行い、該当する表現を修正する。ビルド検証とは別に、文章の検査として実施する。
9. `uv run mkdocs build --strict` を実行し、リンク、フロントマター、Markdown、MkDocs設定を検証する。失敗した場合は原因を直して再実行する。
10. 最後に変更ファイル、ブランチ名、検証結果を報告する。コミット、push、PR作成は依頼された場合だけ行う。

## タイトル・大見出しの検査

ユーザーは、整いすぎた抽象的なタイトルや見出しより、本人の言葉で具体的な出来事を伝える表現を好む。AIが書いたかどうかを判定するのではなく、以下の観点で読み直す。

- タイトルとH2を抜き出し、関連・直近の記事と並べて語調を確認する。見出しだけでも、何を使い、何が起き、何を確かめた記事かが伝わるか。
- ユーザーが話した言葉や、面白いと感じた出来事が残っているか。抽象的な教訓や活動理念に置き換えていないか。発言にない感情や体験は補わない。
- 他の技術名に差し替えても成立する標語、きれいな対句、不要な「〜から〜へ」などの型に頼っていないか。特定の語句を一律に禁止せず、この記事の内容を具体的に伝えているかで判断する。
- 例えば「ベクトル検索を試し、見つけた問題をOSS本家へ返す」より「LanceDBとSQLite vec1を試していて見つけた不具合の話」のように、対象と出来事を直接書く。「実験と実装を行き来する」のような大見出しも、本文に即して具体化するか、独立した節が不要なら省く。この例を毎回の定型にはしない。
- 本文にも、自己評価、言い訳、思考過程の繰り返しがないか確認する。専門性や貢献は、再現条件・切り分け・修正などの事実で示す。結果の理解に必要な制約や不確実性は簡潔に残す。

タイトルや見出しを毎回ユーザーに書いてもらう承認手順は設けず、まずこの検査に基づいて提案・修正する。ユーザー自身の案がある場合は、その意図と語感を優先する。

## 推奨すること

- 冒頭だけで記事の主題と読者が得られる情報が分かるようにする。
- 関連する過去記事を自然な文脈で1件以上リンクし、サイト内で内容をたどれるようにする。
- 一文を長くしすぎず、誇張、過度な自己評価、言い訳に見える説明を避ける。
- 技術用語は既存記事の表記に合わせ、初出時に必要最小限の説明を加える。
- 箇条書きや表は、比較や要点整理に役立つ場合だけ使う。
- 画像を追加する場合は `docs/assets/images/YYYY-MM-DD-<slug>.*` を基本とし、意味のある代替テキストを付ける。
- 公開前に差分を読み直し、日付、固有名詞、相対リンク、未公開情報の混入を確認する。
